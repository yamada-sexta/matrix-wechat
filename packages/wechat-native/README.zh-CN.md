# 微信原生集成

[English](README.md) | [简体中文](README.zh-CN.md)

此工作区负责注入到固定版本微信进程中的代码。它的 TypeScript 项目使用 Frida 类型，与 Bun 运行时应用独立。仓库根目录的检查覆盖这两个项目。运行时将 `src/instrument.ts` 打包到镜像中，并通过此包的导出加载配置。

`native/download.cc` 在微信原生协程队列中实现原图请求。原生查找、载荷复制、下载、异常处理和捕获资源清理均在编译后的回调内部完成。Frida 层仅调用其不会让出执行权的生产者接口和轮询接口。账号或会话代次变化会使过期任务失效；请求有明确的资源限制，并在 JavaScript 超时后保有各自的状态。该库会保持加载，直到进程退出。

所有原生地址均为原始 ELF 的相对虚拟地址（RVA），并通过指令字节和函数边界验证。适配器将异常处理转发给主程序隐藏的运行时：随客户端提供的 `libowl.so` 使用独立的异常线程局部存储（TLS）键，不能为主程序抛出的异常提供捕获运行时。

使用固定版本客户端的 `libowl.so` 在本地构建：

```sh
bash packages/wechat-native/scripts/build-native.sh /path/to/opt/wechat packages/wechat-native/dist
```

脚本会测试动态加载的适配器，包括取消、复制、账号或会话切换、异常清理，以及超时后的资源归属；然后构建生产库并检查异常符号绑定。运行时 Dockerfile 在 CI 中执行相同脚本，生产镜像不包含编译器。真实环境中的自动请求仍需先通过运行时针对具体消息的原图下载验证。

`native/query.cc` 在现有的专用只读 FULLMUTEX 连接上批量执行 SQLite 查询和结果提取。查询库是必需组件，不保留 JavaScript 查询回退路径；它与下载库分开构建，不改变下载验证凭据。数值格式化暂时使用 C 数值区域设置和就近舍入，并在返回前恢复原状态。构建测试需要 Bun、SQLite 开发库和 `de_DE.UTF-8` 区域设置。
